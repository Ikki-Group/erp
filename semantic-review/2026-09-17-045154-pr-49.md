# Server-side date-range filter across POS orders and inventory lists

Four list screens (POS orders, inventory transfers, opname, receiving) had a date-range control that only `.filter()`'d the current page client-side, so pagination and the total count reflected the unfiltered server set — the filter silently lied across page boundaries. This change pushes the range down to the server: `dateFrom`/`dateTo` are added to the four list contracts and the matching web FilterDtos, each repo applies `gte`/`lte` in its `#buildWhere` (orders on `orderedAt`, the other three on `createdAt`), the routes feed the range into query params, and the client-side `useMemo` slice blocks are deleted. Changing the range resets to page 1. The pattern is copied verbatim from the existing `AuditLogFilterDto` + `audit.repo.ts`, which already did exactly this.

Watch for: the range bounds are inclusive on both ends via `gte`/`lte` (confirmed), which means a `dateTo` sent as a midnight `toISOString()` excludes almost the entire target day — a UX/inclusivity pitfall inherited from the audit pattern, not a regression (likely). The two new test files cannot run locally (no test DB) and are CI-only; the transfer test's `SEED_WAREHOUSE_ID = 2` depends on serial-ID seeding staying gapless (confirmed correct on a reset DB, fragile by construction).

**Verdict**: APPROVED

## High-level view

The server side is mechanical and consistent: every repo gained the same two-line `gte`/`lte` guard inside its existing `allOf(...)` where-builder, so the range composes with the status/search/location filters already there rather than replacing them. Orders correctly filter on `orderedAt` (the business timestamp, also the sort column and part of a composite index), and the three inventory lists filter on `createdAt` (their sort column). All four timestamp columns are `notNull`, so no rows are silently dropped by the join to a null date.

The web change is a straight deletion: the `rawData` → `useMemo(filter)` → `data` chain collapses to `data = listQuery.data?.data ?? []`, and the range is passed into the query args as `dateRange?.from.toISOString()`. `DateRange` types `from`/`to` as non-optional `Date`, so the optional chaining is safe and `undefined` flows through cleanly when no range is set. The `useMemo` import stays live in all four files (used for column defs), so no dead import is left behind.

The date-range control resets to page 1 on change via `if (search.page !== 1) navigate(...)`. Page lives in the URL while the range lives in component state; the refetch is driven by the range being in the query key, so a range change on page 1 refetches without a navigate and the reset only fixes the stale-page case after narrowing.

The inclusive/inclusive bound is the one behavioral thing to weigh. `lte(col, dateTo)` means a `dateTo` of `2026-09-17T00:00:00Z` matches only the first instant of the 17th, so a user picking "to: Sep 17" gets nothing from the 17th — an off-by-a-day that depends on how the picker constructs `to`. Inherited from the audit pattern the ticket asked to copy.

The tests prove cross-page correctness in the way that matters (a past-only window must exclude a just-created record _and_ the returned count must honor the window), but they lean on a shared concurrently-seeded DB and on wall-clock windows, which makes them correct-but-brittle rather than tautological.

1. **Inclusive `dateTo` upper bound** — `lte(col, dateTo)` is inclusive, so a midnight-based `dateTo` excludes the whole target day; confirm the web date picker sends an end-of-day `to` or switch the server bound to an exclusive `< dateTo + 1 day`. Inherited from the audit pattern (likely).
2. **No `createdAt` index on the three inventory tables** — transfer/opname/receiving filter+sort on `createdAt` with no supporting index; fine at current volume, a `(location_id, created_at)` index is the eventual fix (possible, low priority).
3. **`SEED_WAREHOUSE_ID = 2` relies on gapless serial IDs** — the transfer test's `toLocationId` assumes WH-01 lands at id 2, true only on a fresh reset; documented but fragile (confirmed).
4. **Time-window tests are brittle under clock/seed assumptions** — correct today because seeded orders sit ~30 min in the past, but a future backdated seed or a >100-row straddling window would break the `limit: 100` include assertion (possible).

### Server range filtering composes, doesn't replace

Each repo adds the guard inside the existing `allOf(...)`, next to the status/location/search predicates, so the range ANDs with everything already there:

```ts
// order.repo.ts #buildWhere
eq(orders.locationId, filter.locationId),
eqIf(orders.status, filter.status),
eqIf(orders.shiftId, filter.shiftId),
filter.dateFrom ? gte(orders.orderedAt, filter.dateFrom) : undefined,
filter.dateTo ? lte(orders.orderedAt, filter.dateTo) : undefined,
searchAcross(filter.q, [orders.orderNo]),
```

`allOf`/`eqIf` drop `undefined` predicates, so an absent bound contributes nothing. Orders filter on `orderedAt`; transfer/opname/receiving on `createdAt`. The column choice matches each list's sort key — `orderedAt` (also part of `orders_location_status_ordered_idx`) for orders, `createdAt desc` for the inventory trio — so filtering and sorting agree. The transfer repo appends the two date guards after its `fromLocationId OR toLocationId` raw-SQL predicate without disturbing it.

All four columns are `timestamptz notNull defaultNow`, so the range never silently drops a row for a null timestamp — a real trap this avoids.

Both bounds are inclusive (`gte`/`lte`). A `dateTo` sent as a day-start ISO string (`...T00:00:00Z`) matches only rows at that exact instant, excluding the target day — the "my filter for today returns nothing" off-by-a-day. Mirrors `audit.repo.ts` exactly; confirm the picker emits an end-of-day `to`.

### Web: deletion over addition, no leftover

The change is the lazy-correct one — the client filter is gone, not reworked:

```ts
// before: rawData + useMemo(() => rawData.filter(...)) + data
// after:
const data = listQuery.data?.data ?? []
```

`dateFrom`/`dateTo` go into the query args as `dateRange?.from.toISOString()` / `.to.toISOString()`. `DateRange` (`components/shared/date-range-filter.tsx`) declares `from: Date` and `to: Date` as required, so once `dateRange` is defined both fields exist — the optional chain guards only the whole-object-undefined case and `undefined` args mean "no bound." `rawData` is removed in all four files with no orphaned reference; `useMemo` stays imported because every route still uses it for column defs, so no unused-import hit. The page-1 reset (`if (search.page !== 1) navigate(...)`) is identical across all four routes and spreads `search`, so no other URL params are clobbered; `navigate` and `dateRange`/`setDateRange` are in scope in every file (verified).

### Tests prove the cross-page claim, but lean on the shared DB

The POS test and the new `inventory-date-filter.test.ts` both use the same shape: create a record (lands at "now"), assert a straddling `now±1h` window includes it, then assert a `now-48h..now-24h` window excludes it _and_ that every returned row falls inside that past window. The past-window case is the one that actually proves the fix — under the old client-only filter the record would still be counted in `meta.total` and could appear on another page; here the exclusion is server-authoritative. This is not tautological.

Two brittleness sources to note rather than fix:

- The suites run concurrently against one seeded DB. The include assertion uses `limit: 100`, so if concurrent tests ever created >100 records inside the straddling hour, the target could fall off page 1 and flake. Unlikely at current test volume.
- The past-window exclusion depends on nothing being seeded 24–48h in the past. The sample order is seeded at `NOW() - INTERVAL '30 minutes'` (`sample-order.ts`), comfortably outside the past window, so the `for` loop over `past.data` holds today. A future backdated seed fixture would silently break it.

The `inventory-date-filter.test.ts` transfer case posts `toLocationId: SEED_WAREHOUSE_ID`. `seedLocations` inserts STORE-01 then WH-01 with serial IDs, so WH-01 = 2 on a clean reset — the new `SEED_WAREHOUSE_ID = 2` constant is correct. It's coupled to gapless serial assignment, which the seed helper's "reset first" contract guarantees, but it's an implicit dependency rather than a looked-up id.

### Consistency across the four modules

The four repos, four server contracts, four web DtOs, and four routes are done identically — same guard shape, same `z.coerce.date()` on the server, same `z.string()` on the web, same page-1 reset. No module is missing the range and no route skips the reset. The only cross-module variance is the intended one: orders key off `orderedAt`, the inventory trio off `createdAt`.

### Serialization boundary

Web sends `z.string()` ISO via `toISOString()` (always UTC `Z`), server parses with `z.coerce.date()` — round-trips UTC with no wire-level drift. The only timezone question is upstream of this diff: how the picker chose local day boundaries before `toISOString()`. Combined with the inclusive `lte`, that upstream choice is where a day gets clipped.
