# Server-authoritative order totals in the POS new-order screen

Ticket #50 removes the client's order-money arithmetic from the POS new-order screen, implementing ADR-0017. The hard-coded `TAX_RATE = 0.11` and the client `taxAmount`/`total` computations are deleted. Tax and grand total are now sourced from the server: opening payment syncs the cart (`lines/sync`), fetches the order detail, and drives the payment dialog off `Number(detail.data.total)`. The cart shows tax and total as "Dihitung saat bayar" (pending) until that point. `handlePaymentConfirm` no longer syncs lines — it records payments and completes against `currentOrderId`.

Watch for: a residual client-side money computation — the `subtotal` line sum — is still rendered as the cart's "Subtotal" (confirmed); ADR-0017 bans client arithmetic that produces an order's money, and this is exactly that. A double-click on "Bayar" can create two orders because `createOrderIfNeeded` guards on state that hasn't updated yet (likely). Both are the notable items; the payment flow's stale-total and no-resync concerns are real on the client but backstopped fail-closed by the server.

**Verdict**: NEEDS_CHANGES

## High-level view

The money flow is genuinely server-authoritative for tax and total now. `taxAmount` and `total` are hard-wired to `null` from the parent and rendered as pending; the payment dialog collects against the server total fetched after sync. The one hole in the letter of ADR-0017 is `subtotal`: it's still a client `useMemo` reduction over cart-line prices (`(unitPrice + modifierTotal) * qty`), and the cart renders it as the "Subtotal" row — a client-computed order money amount, not a per-line catalog price. The ADR's carve-out is for rendering a server-provided per-line price, not for summing lines into an order subtotal.

Splitting payment into open-then-confirm introduces a gap between when the total is captured and when it's paid. On the client this is unguarded (a voucher applied while... it can't be — the dialog is modal), but the real protection is server-side: both `handleRecordPayment` and `handleComplete` re-validate payment amounts against their own `order.total`, so a stale client `paymentTotal` fails closed rather than under/over-charging. Worth knowing the safety lives on the server, not the client.

The confirm path correctly assumes lines were synced at open, and there's no path to confirm without opening first. State resets are complete on success; on cancel, `paymentTotal` is reset via the `onOpenChange` wrapper. The remaining client-side risk is a double-fire of "Bayar" creating duplicate orders, shared with the pre-existing voucher path but now on the hot payment path.

## Subtotal: the one client money computation left standing

ADR-0017's rule is precise: "the client never computes a monetary amount," with a single carve-out for "a per-line unit price shown while browsing the menu ... the rendering of a server-provided price." The diff deletes `taxAmount`/`total` but keeps:

```ts
// new-order.tsx:88
const subtotal = useMemo(
	() => lines.reduce((sum, line) => sum + (line.unitPrice + line.modifierTotal) * line.qty, 0),
	[lines],
)
```

and `order-cart.tsx:143` renders it under the label "Subtotal". That is client-side arithmetic aggregating an order's money — the "second source of truth" the ADR names, differing only in that no tax is applied. The server computes and persists its own `subtotal` (per the ADR's own description of `calculateOrderTotals`), so this can drift the same way tax could: a modifier price the client hasn't refetched, a rounding rule, a line the server merged differently. The comment in the code calls it "a preview of server-provided prices, which ADR-0017 permits" — but the ADR permits rendering a _per-line_ price, and this is the summed order subtotal, not a line price.

This is the gap between the letter of the ADR and the implementation. Two clean options: pass the server subtotal (from the same `detail` fetch that gives the total) and show it pending pre-sync like tax/total, or drop the subtotal row's numeric value until sync. The per-line `lineTotal` rendered inside each cart row (`order-cart.tsx:70`) is closer to the carve-out — it's a single line's price × qty — though strictly it's still a multiplication; if you want to be conservative that's a line price straight from the catalog DTO and is defensible. The aggregated subtotal is the one that clearly crosses the line.

## Payment split: what the open/confirm gap does and doesn't expose

The flow moved from "confirm does everything" to "open syncs + fetches total, confirm records + completes":

```
Bayar → handleOpenPayment
          createOrderIfNeeded → linesSync → fetchQuery(detail) → setPaymentTotal(total) → open dialog
Selesaikan → handlePaymentConfirm
          (currentOrderId guard) → paymentMut per entry → completeMut → fetch receipt → reset
```

The dialog is modal, so the cart can't be edited and no voucher can be applied while it's open — the "user changes total between open and confirm" scenario isn't reachable through the UI. Where a stale `paymentTotal` _could_ bite is a concurrent session or a slow network re-ordering, and there the server is the backstop: `handleRecordPayment` rejects any amount exceeding `order.total - sumPaid` (`paymentExceedsTotal`), and `handleComplete` throws `notFullyPaid` when `order.total - sumPaid > 0`. So a client total that's too low leaves the order un-completable (fail-closed), and one that's too high is capped per-payment. The client never over- or under-charges silently. The cost is only UX: the confirm catch shows the generic "Gagal memproses pembayaran" with no hint that the displayed total was stale.

## Confirm without a prior sync: not reachable

`handlePaymentConfirm` opens with `if (!currentOrderId) return`, and the only way the dialog opens is `handleOpenPayment`, which sets `currentOrderId` (via `createOrderIfNeeded`) and awaits `linesSync` before `setShowPaymentDialog(true)`. There is no other caller of `setShowPaymentDialog(true)` in the file. So by the time confirm can fire, lines were synced for that `currentOrderId` — the removal of the sync from confirm is safe. One nuance: confirm captures `orderId = currentOrderId` at call time, so even if a reset raced in, it operates on a consistent id. Good.

## Double-click on "Bayar"

The button is `disabled={disabled || lines.length === 0}` where `disabled` is `isBusy` (`new-order.tsx:302`, `order-cart.tsx:178`). `isBusy` only becomes true after a mutation reports `isPending` and React re-renders. Two synchronous clicks dispatched before that render both enter `handleOpenPayment`; both call `createOrderIfNeeded`, which checks `if (currentOrderId) return currentOrderId` — but `setCurrentOrderId` from the first call hasn't flushed, so the second call also sees `null` and fires a second `createMut.mutateAsync`, producing a duplicate order. `linesSync` then targets whichever id each closure captured. This pattern pre-exists on `handleApplyVoucher` (same `createOrderIfNeeded` race), so it isn't introduced here, but ticket #50 moves it onto the primary checkout button where a double-tap is most likely. A ref-based in-flight guard or disabling on `createMut.isPending || linesSyncMut.isPending` synchronously would close it.

## State reset across success and cancel

On success `paymentTotal` is nulled in both the success block (`new-order.tsx:256-262`) and again by the `onOpenChange` wrapper when `PaymentDialog.handleConfirm` closes the dialog (`new-order.tsx:322-327`) — a harmless double-reset. Cancel/close resets `paymentTotal` through that same wrapper, and the dialog clears its own `entries`. No stale `paymentTotal` survives either path.

## Dead render branches and leftovers

`OrderCart`'s `taxAmount`/`total` props are typed `number | null` but the parent only ever passes `null` (`new-order.tsx:302-303`), so the non-null render branches are unreachable from this screen. The "upgrade path" comment describes a future debounced live-sync that would pass real numbers, so keeping the props general is a defensible bet — flagging only so a reader knows the numeric branch is currently untested and unhit. No unused imports or leftover state: `useMemo` still backs `subtotal`, `TAX_RATE` is gone, and `handlePaymentConfirm`'s dependency array was correctly trimmed to `[currentOrderId, paymentMut, completeMut, queryClient]`.
