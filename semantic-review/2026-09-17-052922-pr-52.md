# Audit-log browser route (#52)

Adds a filterable audit-log browser at `/settings/audit` following the established list-page template (`listSearchSchema` + `useServerTable` + URL search state), gated on `audit.read`, with a per-row detail dialog. The web `AuditLogFilterDto` switches `dateFrom`/`dateTo` from `z.coerce.date()` to `z.string()` so the route can send `.toISOString()`, matching the `pos/orders.tsx` (#49) pattern. This wires up `auditResource.detail`, which had no prior consumer (`auditResource.list` was already live on the dashboard, so only `detail` was actually dead).

Watch for: the detail dialog keeps showing the previous row's data for a beat when you click a second row, because the query is `enabled` continuously and the stale `data` renders while the new id refetches (confirmed). Row-click-to-open has no keyboard affordance — the detail dialog is unreachable without a mouse (confirmed). The `dateRange` filter lives in local `useState`, so it is lost on reload and not shareable via URL, unlike the module/action filters which persist in the URL (confirmed) — though this mirrors the pre-existing `pos/orders.tsx` pattern.

**Verdict**: NEEDS_CHANGES

## High-level view

The route is a faithful clone of the users/orders list template: `auditSearchSchema` extends `listSearchSchema` with `module`/`action`, those two filters round-trip through URL search state, and `useServerTable` drives pagination and the global search filter. Date range is the one filter held in component state rather than the URL, matching how `pos/orders.tsx` already does it — a deliberate, if inconsistent, house pattern rather than a defect introduced here.

Permission gating is enforced two ways that agree: the list query is `enabled: canRead` so no fetch fires without `audit.read`, the component early-returns a "no access" empty state, and the server independently returns 403. There is no client path to data without the permission.

The detail dialog's `id: entryId!` assertion is safe (the query only runs when `entryId` is non-null). The gaps are UX, not correctness: because the query stays enabled and mounted, switching rows shows the prior entry's values until the refetch resolves, and there is no keyboard route to trigger the row click at all.

The date-serialization DTO change is consistent with #49 — both send ISO strings the server's `z.coerce.date()` parses, and the two server tests exercise a module filter and a future-window range that must return zero rows.

`MODULE_OPTIONS`/`ACTION_OPTIONS` are hardcoded and will drift from the server vocabulary over time.

### Filter wiring and the URL-vs-local split

The list query composes cleanly from search state and the local date range:

```tsx
...auditResource.list.queryOptions({
  page: search.page, limit: search.pageSize, q: search.q,
  module: search.module, action: search.action,
  dateFrom: dateRange?.from.toISOString(),
  dateTo: dateRange?.to.toISOString(),
}),
enabled: canRead,
```

`module` and `action` are validated into the URL via `auditSearchSchema` and their `onChange` handlers reset `page: 1`, so paging never strands you on an out-of-range page after narrowing. `q` flows through `useServerTable`'s global filter. The `dateRange` `onChange` also resets to page 1 when needed.

The one asymmetry is state location: `module`/`action`/`q`/`page` live in the URL and survive reload and link-sharing; `dateRange` lives in `useState(undefined)` and is lost on reload. This is the same split `pos/orders.tsx` already ships (local `dateRange` state, `.toISOString()` into an identical `z.string()` DTO), so it is a house pattern, not a regression in this PR. Worth a deliberate call: if audit ranges are meant to be shareable/bookmarkable, they need to move into the search schema; if not, the current approach is consistent with the codebase.

### Detail dialog: stale body, missing keyboard entry

```tsx
const detailQuery = useQuery({
	...auditResource.detail.queryOptions({ id: entryId! }),
	enabled: entryId !== null,
})
```

The `entryId!` assertion is sound. The behavioral gap is staleness: the dialog stays mounted and the query stays enabled across row switches, so clicking a second row while the first is still cached renders the _previous_ entry's fields (including `oldValues`/`newValues`) until the new id resolves. Because the query key includes the id this is a transient flash rather than permanently-wrong data, but for an audit view — where the whole point is attributing a specific change — showing row A's diff under row B's header is misleading. Reset the dialog subtree with `key={detailId}` or gate the body on a matching/settled fetch.

Row-click is wired only through the row's mouse `onClick` in `data-grid-table.tsx` (no `tabIndex`, `role`, or Enter handler), so the detail dialog is unreachable by keyboard — a WCAG operability gap given this is the sole path to a row's detail.

The JSON blocks stringify `oldValues`/`newValues`/`metadata` (`z.unknown()`), null-guarded. React escapes the content so there is no injection vector, but there is no size bound — a large payload renders in full inside the dialog.

### Date serialization change matches #49

```ts
// dateFrom/dateTo: z.coerce.date() → z.string()
dateFrom: z.string().optional(),
dateTo: z.string().optional(),
```

`buildSearchParams` does `String(value)` on query params, so a `Date` would serialize to a locale string the server can't parse; sending `.toISOString()` and typing the field as `z.string()` is exactly what `pos/orders.tsx` + `OrderFilterDto` (#49) already do, with the server keeping `z.coerce.date()` to parse it back. The two new server tests cover this end to end: a `module: 'iam'` filter asserts every returned row is `iam`, and a future-only window asserts `data.length === 0` and `meta.total === 0` — a clean negative proving the range actually bounds the query rather than being ignored.

### Hardcoded option lists

`MODULE_OPTIONS` and `ACTION_OPTIONS` are hand-maintained arrays with no compile-time tie to the server's module/action vocabulary, so adding a module server-side leaves it silently unfilterable here until someone updates this file. A maintenance smell rather than a bug — worth a comment pointing at the server source of truth. (`actionVariant` in the columns file at least degrades unknown verbs to a neutral badge rather than throwing.)

### Dead-code retirement

`auditResource.detail` had no prior consumer and is now used by the dialog — genuinely retired. Note `auditResource.list` was _already_ consumed by the dashboard (`routes/_authenticated/index.tsx`, recent-activity widget), so the "retires the dead endpoints" framing is half accurate: `list` was already live; only `detail` was dead before this change.
