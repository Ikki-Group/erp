# Dashboard wired to real data from existing endpoints (honest subset)

The dashboard route was 100% hardcoded arrays and literal stat values. This rewrite replaces every panel with data from endpoints that already exist — order/shift counts via list `meta.total`, low-stock via a client-side predicate over the stock-balance list, and recent activity via the audit log — and deliberately marks the two panels that would require a real server aggregation (revenue trend, category sales) plus the revenue stat as "Segera" / "Segera hadir" coming-soon states rather than faking them. Money is never summed on the client, honoring ADR-0017: revenue is punted to the server, and the low-stock predicate compares quantity-vs-minimum (both non-money decimals). Location-scoped metrics gate on `activeLocation.id` and render em-dash / "Pilih lokasi" in the consolidated (all-locations) view.

Watch for: nothing blocking. The "count via `limit: 1` + `meta.total`" pattern is correct against the paginated response contract (confirmed). The `useMemo([])` around `todayRange()` is genuinely required, not cargo-culted (confirmed). The low-stock predicate reads the top-200 balances and filters client-side — a bounded, documented approximation worth noting but not fixing here (confirmed). One minor honesty nit on the low-stock stat count vs. the "top 6" panel (possible).

**Verdict**: APPROVED

## High-level view

Each of the four metrics is wired to an endpoint that already exists, and the wiring matches the DTO contracts: `OrderFilterDto` and `ShiftFilterDto` both take a required `locationId` plus the optional filters used here (`dateFrom`/`dateTo`, `status`), and the paginated envelope carries `meta.total`, so fetching with `limit: 1` and reading `meta.total` is the right way to get a count without pulling rows. Field names on the rendered rows (`materialId`, `materialName`, `materialCode`, `quantity`, `uomCode`, `minStock`; `id`, `summary`, `userName`, `timestamp`) all line up with `StockBalanceDto` and `AuditLogDto`.

Consolidated-view handling is safe. `isConsolidated` is defined as `currentLocation === null` in the location provider, which is exactly the condition under which `locationId` is `undefined`; the two are equivalent, so a card never sits in the disabled-query limbo showing `'…'` forever. The `locationId!` non-null assertions are type-level only — `enabled: locationId !== undefined` stops the query function from ever running with a bad value.

The refetch-loop fix is real. `todayRange()` calls `new Date()`, so an un-memoized call produces millisecond-different ISO bounds every render; those unequal strings change the query-key hash each render and would loop. Memoizing with `[]` freezes the bounds at mount, and the ponytail comment correctly names the midnight-rollover ceiling.

ADR-0017 is honored: no client-side money arithmetic. Revenue is explicitly deferred to a server aggregation, and the low-stock comparison is quantity-vs-minimum (both `zp.decimal` non-money quantities).

Loading / error / empty states are present on all three data-backed panels, matching the ikki-design floor (skeleton rows, inline error, composed empty state — not a bare spinner). No dead imports or dangling exports result from deleting the charts and the order-status `SegmentedBar`.

### Consolidated view: equivalence makes the guard airtight

```
locationId = activeLocation?.id
isConsolidated ≡ (currentLocation === null)   // from location-provider
```

`locationId === undefined` ⇔ `activeLocation === null` ⇔ `isConsolidated === true`. Because the render branches key off `isConsolidated` and the query `enabled` keys off `locationId !== undefined`, there is no window where a card falls through to `todayOrders ?? '…'` while its query is disabled — the `isConsolidated ? '—'` branch always wins in that state. So no card gets stuck on the `'…'` placeholder, and no NaN: the `locationId!` assertions never execute against `undefined` because `enabled` short-circuits the fetch.

### The `useMemo([])` is load-bearing

The key subtlety: TanStack hashes query keys structurally, so a _fresh-but-equal_ object would not by itself loop. But `todayRange()` builds its bounds from `new Date()` at call time, so each render yields `dateFrom`/`dateTo` that differ at the millisecond — genuinely unequal values, a different hash, a refetch every render. `useMemo(() => todayRange(), [])` pins them at mount and breaks the loop. The comment's stated ceiling (bounds stale after a midnight rollover until reload) is the honest tradeoff and is marked `ponytail:`.

### Low-stock predicate — correct, and bounded

```ts
;(stockQuery.data?.data ?? []).filter(
	(b) => b.minStock !== null && Number(b.quantity) < Number(b.minStock),
)
```

The `!== null` guard is required before `Number(...)`: `minStock` is `zp.decimal.nullable()`, and without the guard `Number(null)` would coerce to `0` and misclassify a null-minimum material as low. The caveat is the source cap: the balances list is fetched at `limit: 200`, so on a location with more than 200 stock rows the count and the panel silently see only the first page. Unlike `todayRange`, this corner isn't flagged with a ceiling comment — a single `ponytail:` line naming the 200-row cap would make it explicit.

### Cleanup

Deleting the two charts drops `AreaChart`, `BarChart`, and `ChartConfig`; deleting the order-status card drops `SegmentedBar` and `WalletIcon` — all removed from imports, and `tsc --noEmit` passes clean. `SegmentedBar` stays exported from the shared barrel because `design-system.tsx` still uses it, so that export is not newly dead. Removing the hardcoded order-status card loses nothing real: its 108/14/6 split was invented, and an honest status distribution needs the same server aggregation as revenue.
