# Task-Driven Workflow

Manage features and issues through structured markdown files in `.ignore/tasks/`.

## Trigger

Activate this steering when:

- User sends a markdown draft / feature idea / bug report / issue description
- User references an existing task file (e.g., "continue TASK-003")
- User says "grooming", "breakdown", "plan this"

---

## File Convention

| Rule          | Value                                                     |
| ------------- | --------------------------------------------------------- |
| Location      | `.ignore/tasks/`                                          |
| Naming        | `TASK-{NNN}-{kebab-slug}.md`                              |
| ID Assignment | Scan existing files, increment highest number             |
| Status Values | `DRAFT` → `GROOMING` → `IN_PROGRESS` → `DONE` / `BLOCKED` |

---

## Template

Every task file uses the following structure:

```markdown
# TASK-{NNN}: [Short title]

## Meta

| Field    | Value      |
| -------- | ---------- |
| Status   | DRAFT      |
| Created  | YYYY-MM-DD |
| Updated  | YYYY-MM-DD |
| Sessions | 1          |

---

## Draft

[Raw user input — never modified after grooming]

---

## Contract

### Problem Statement

[1-2 sentences: what's the problem / what we want to achieve]

### Acceptance Criteria

- [ ] Criterion 1
- [ ] Criterion 2
- [ ] Criterion 3

### Scope

- **In scope:** ...
- **Out of scope:** ...

### Technical Context

[Relevant files, modules, dependencies — filled after codebase research]

### Task Breakdown

1. First task
2. Second task
3. ...

### Manual Test Checklist

Generated by Kiro after task breakdown. User runs these manually to verify.

**Happy Path:**

- [ ] Test scenario 1 — expected result
- [ ] Test scenario 2 — expected result

**Negative Cases:**

- [ ] Invalid input / missing required field — expected error
- [ ] Unauthorized access — expected rejection

**Edge Cases:**

- [ ] Boundary condition — expected behavior
- [ ] Concurrent / race condition — expected behavior

---

## Progress Log

### Session 1 — YYYY-MM-DD

**Completed:**

- [x] What was done

**Changes:**
| File | Action | Description |
|------|--------|-------------|
| `path/to/file` | created/modified/deleted | Brief description |

**Decisions:**

- Decision and reasoning (the why, not just what)

**Next Steps:**

- What needs to be done next (specific & actionable)
```

---

## Phase 1: DRAFT

When user sends a new idea/draft:

1. Scan `.ignore/tasks/` to determine next ID
2. Create file `TASK-{NNN}-{slug}.md` using template
3. Copy user's raw input to `## Draft` section — verbatim, no edits
4. Set status = `DRAFT`
5. Immediately proceed to Phase 2

---

## Phase 2: GROOMING

Transform draft into a structured contract:

1. **Understand the draft** — read and comprehend user intent
2. **Research** — explore codebase (read files, grep patterns, check existing modules), read docs, fetch web resources if needed. Free to use any available tool.
3. **Fill the Contract section:**
   - Problem Statement — concise and clear
   - Acceptance Criteria — testable, checklistable
   - Scope — explicit in/out to prevent scope creep
   - Technical Context — file paths, module names, dependencies, architecture notes from research
   - Task Breakdown — numbered, incremental, each task produces working code
   - Manual Test Checklist — happy path, negative cases, and edge cases for user to verify manually
4. **Update status** → `GROOMING`
5. **Present contract to user** — show summary, ask for confirmation or adjustments
6. Once user confirms → status = `IN_PROGRESS`

### Grooming Rules

- Task breakdown must be incremental — each task builds on previous
- No orphaned code — every task ends with integration
- Include test requirements where appropriate
- Each task must be completable within a single session
- If a task is too large, split into sub-tasks

---

## Phase 3: EXECUTION

When working on tasks (status = `IN_PROGRESS`):

1. **Read the task file** — understand context, check latest progress log
2. **Work through Task Breakdown sequentially** — never skip or work out of order
3. **At end of every session**, MUST append to `## Progress Log`:

```
### Session N — YYYY-MM-DD

**Completed:**
- [x] Items completed this session

**Changes:**
| File | Action | Description |
|------|--------|-------------|
| `path/file` | created | Description |
| `path/file` | modified | What was changed |

**Decisions:**
- Decisions made and their reasoning

**Next Steps:**
- Specific tasks to continue in the next session
```

4. **Update Meta table** — increment Sessions count, update `Updated` date
5. **If all Acceptance Criteria are met** → status = `DONE`, check all AC items

---

## Phase 4: RESUMPTION

When user references an existing task in a new session:

1. Read the task file completely
2. Check the last Progress Log entry — focus on "Next Steps"
3. Continue from where the previous session left off — DO NOT redo completed work
4. Increment session counter in Meta

---

## Progress Log Standards

The progress log serves as **learning context** for future sessions. Write it so that:

- A new session can understand the full state without additional questions
- Decisions include the _why_ (not just what was decided)
- Changes table is exhaustive — every created/modified/deleted file is listed
- Next Steps are specific and actionable (not vague "continue working on X")
- If there are blockers or issues, document them clearly

---

## NEVER Do

- Never start coding without reading the task file first
- Never skip the grooming phase — even "simple" tasks get a contract
- Never leave a session without updating the Progress Log
- Never delete task files — they are permanent archives
- Never modify the Draft section after grooming (it's a historical record)
- Never work on tasks out of order from the Task Breakdown
- Never create task files outside `.ignore/tasks/`
- Never reuse an existing ID — always increment from the highest
